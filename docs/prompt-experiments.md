# Prompt 工程对照实验记录

> LEARNING_PLAN.md 第 2 周 Prompt 工程练习的实验记录。 实验环境:本工程 chat
> 页面(v8+),双模型下拉切换,temperature 0.7 固定。
> **模板创建**:2026-11-09 | **实验数据**:2026-11-10(30 组跑批,脚本 run_experiments.py,原始结果 experiment_results.json)

## 实验纪律(每次实验前重读)

1. **一次只变一个变量**:同组对照除被测因素外,prompt 一字不差,参数不动
2. **每个实验跑 2-3 遍再下结论**:7B 级小模型方差大,单次结果不可信
3. **每个实验用新会话**:刷新页面(新 conversationId),避免记忆污染对照
4. **结论写具体**:写"3 次里错 2 次,加 XX 后 3 次全对",不写"有效/无效"

## 实验一:思维链(CoT)

**测试题**:一个商店打 8 折后再打 9 折,相当于打几折?为什么? (变体可换数字:鸡兔同笼 /
浓度混合 / 日期推算)

### 对照组 A:无 CoT

```
一个商店打8折后再打9折,相当于打几折?
```

### 对照组 B:CoT

```
一个商店打8折后再打9折,相当于打几折?请一步一步思考,先算出8折后的价格系数,再算出叠加后的最终系数,最后给出结论。
```

### 记录表

| #   | Prompt   | 模型           | 第1次 | 第2次 | 第3次 | 备注 |
|:----|:---------|:---------------|:-----|:-----|:-----|:-----|
| 1.1 | A(无CoT) | qwen2.5        | ✅7.2折 | ✅ | ✅ | 3/3 对,均自发给出 100→80→72 步骤 |
| 1.2 | A(无CoT) | deepseek-coder | ❌公式错 | ❌拒绝回答 | ❌结果错 | 0/3:把折扣率当 0.08/0.09 相加;直接说"这是数学问题请找数学专家";步骤对但结论错 |
| 1.3 | B(CoT)   | qwen2.5        | ✅ | ✅ | ✅ | 3/3 对,步骤更规范(按指令先算价格系数) |
| 1.4 | B(CoT)   | deepseek-coder | ✅72元 | ❌"72折" | ❌8折算成92% | 1/3:第2次计算正确但把 0.72 说成"72折"(概念错);第3次折扣概念本身就错 |

**判卷要点**:正确答案 0.8×0.9=0.72 即 7.2
折。看的是**有没有显式中间步骤**,不只看答案对错。

### 结论(2026-11-10 实测,30 请求跑批,脚本 run_experiments.py)

- CoT 对 qwen2.5 的收益:**零**(3/3 → 3/3)。该题在能力区内,CoT 只让步骤更规范,不改变对错
- CoT 对 deepseek-coder 的收益:**有限且不稳**(0/3 → 1/3)。最大作用是把"拒绝回答"掰回"尝试计算";但折扣概念错误(8折=92%、0.72 说成 72 折)是知识层缺陷,CoT 救不了
- 意外发现:①coder 会**拒绝领域外问题**,CoT 能降低拒绝率;②"预判 coder 数学好"完全错误;③qwen 无 CoT 也自发分步推理(通用对话训练已内含轻 CoT)

## 实验二:少样本提示(few-shot)

**测试任务**:把故障描述转成 JSON(time/site/component/severity)

### 对照组 A:零样本

```
把这句话转成JSON:昨天下午三点,北京机房的空调报警,情况严重。
```

### 对照组 B:2-shot

```
把故障描述转成JSON。

示例1:
输入:今早八点,上海机房服务器宕机
输出:{"time":"今早八点","site":"上海机房","component":"服务器","severity":"严重"}

示例2:
输入:昨晚十一点,广州网络丢包率30%,轻微影响
输出:{"time":"昨晚十一点","site":"广州机房","component":"网络","severity":"轻微"}

现在处理:昨天下午三点,北京机房的空调报警,情况严重。
```

### 记录表

| #   | Prompt    | 模型            | 字段齐全? | 格式纯净? | severity推断? | 备注 |
|:----|:----------|:---------------|:---------|:--------|:-------------|:-----|
| 2.1 | A(零样本)  | qwen2.5        | ❌中文键名"时间/地点/事件" | ❌前后带解释文字 | ✅ | 还自作主张把"地点"拆成{城市,设施}嵌套 |
| 2.2 | A(零样本)  | deepseek-coder | ⚠️自造键名 timestamp/location/event | ✅ | ❌"严重"没单独提取,混在 event 里 | 方向对但完全没遵循要求语义 |
| 2.3 | B(2-shot) | qwen2.5        | ✅四字段+顺序全对 | ✅ | ✅"情况严重"→"严重" | 完美复刻示例结构 |
| 2.4 | B(2-shot) | deepseek-coder | ❌偏离 | ❌ | ❌ | **跑去写 Python 解析代码**(用它最熟的"代码"方式解任务),没直接给 JSON |

**判卷要点**:
- 字段齐全:time/site/component/severity 四个都在且名字一致
- 格式纯净:输出只有 JSON,没有"好的,以下是转换结果"等废话
- severity 推断:"情况严重"→"严重"(零样本可能输出原句"情况严重"或漏字段)

### 进阶对照(可选):示例锚定效应

示例里 severity 故意用 "P1/P2" 粒度,看模型是否跟着换粒度 ——
验证**模型模仿示例强于理解指令**。

### 结论(跑完填)

- few-shot 对字段/格式的控制力:**对 qwen2.5 是质变**(键名中文化→精确复刻;嵌套结构→扁平四字段;废话→纯净输出;severity 从"情况严重"正确归一为"严重")。few-shot 不教规则,**示例本身就是规则**
- 两个模型谁更吃 few-shot:qwen2.5 完全吃;deepseek-coder **不吃反而跑偏** —— 2-shot 后开始写 Python 代码来"解析这句话",它对 few-shot 的理解是"这是个编程任务"。代码模型的任务定位惯性极强
- 与运维告警结构化的联想:生产场景做告警/工单结构化,**必须用 few-shot 且必须用通用模型**;coder 类模型会给出"如何用代码实现这个解析"的答案而非答案本身

## 实验三:幻觉抑制

### 测试题(三问,前两问为诱饵)

1. 基线(应答对):`介绍一下Java的垃圾回收机制。`
2. 纯编造(应说不知道):`介绍一下Java
   17中新增的FiberManager类的设计原理。(类名是编的,Java里没有)`
3. 半真半假(更接近真实幻觉):`Spring AI 2.0 中 DeepSeekChatOptions 的
   artifactId 参数是做什么的?(参数是编的)`

### 对照组:约束前缀

```
仅基于你确定知道的事实回答。如果不确定或不知道,直接说"我不知道",不要编造。
[原问题]
```

### 记录表

| #   | 问题           | 约束? | 模型            | 是否编造?    | 编造内容摘要 | 备注 |
|:----|:--------------|:------|:---------------|:------------|:-----------|:----|
| 3.1 | 基线GC         | 无    | qwen2.5        | —(基线应正确) | ✅正常介绍GC | 1290字,质量合格 |
| 3.2 | FiberManager  | 无    | qwen2.5        | **✅编造** | "Java 17引入纤维,FiberManager是管理器接口,设计目的…功能性接口…" | 1018字,一本正经 |
| 3.3 | FiberManager  | 有    | qwen2.5        | **❌未编造** | — | 281字:"Java 17并没有引入名为FiberManager的类",还主动纠错 |
| 3.4 | FiberManager  | 无    | deepseek-coder | **✅编造** | "Java 17引入了全新的类java.util.concurrent.forkjoin.FiberManager…" | 817字,连不存在的包路径都编了 |
| 3.5 | FiberManager  | 有    | deepseek-coder | **✅照编** | "Java 17引入的新FiberManager类就是为此设计…提供纤程创建调度管理" | 1442字,**约束完全无效,编得更多** |
| 3.6 | artifactId参数 | 有    | qwen2.5        | **❌未编造** | — | 108字,干脆的"我不知道" |

**判卷要点**:编造 = 一本正经给出不存在的类/参数的"功能说明"。正确行为 =
承认不知道或指出可疑。

### 结论(跑完填)

- 无约束时编造率:qwen2.5 与 deepseek-coder 均 100%(2/2 都流畅编造)
- 加约束后编造率:qwen2.5 → **0%**(约束完全生效);deepseek-coder → **仍 100%**(约束被无视,编造字数反增 817→1442)
- 小模型对约束的遵循度:**分模型天差地别**。qwen 的对话训练让它把系统约束当指令;coder 的训练分布里"代码生成"压倒一切,提示约束权重不够。结论:**幻觉抑制约束只对通用对话模型可靠,对代码模型基本无效**
- 对 RAG 阶段的意义:①检索为空时**必须在 prompt 层硬性兜底**("仅根据以下资料回答,资料为空则回答未找到"),不能指望模型自觉;②**模型选型决定幻觉治理上限** —— 用 coder 做问答,幻觉约束形同虚设,这是比 prompt 更上层的决策

## 实验四:综合对照矩阵(3×2)

**测试问题**(选一条真实工作中的问题,运维/集成背景优先):

```
排查一个Spring Boot应用内存持续上涨问题的完整思路是什么?
```

### 矩阵:跑 6 次

| #   | 策略      | 模型           | 结果摘要 | 一句话评价 |
|:----|:---------|:---------------|:--------|:---------|
| 4.1 | 裸问      | qwen2.5        | 1209字,监控→日志→代码→JVM参数四段式,提及Prometheus/Grafana/Heap/Metaspace | 结构自发清晰,知识点准确丰富 |
| 4.2 | CoT      | qwen2.5        | 1243字,严格按"现象→怀疑点→验证方法"走 | 与裸问质量相当,CoT 边际收益≈0 |
| 4.3 | few-shot | qwen2.5        | 646字,【现象】【怀疑点】【验证方法】完全复刻模板 | 模板遵从完美,内容密度略降但更可扫读 |
| 4.4 | 裸问      | deepseek-coder | 984字,"理解问题→检查日志→使用Java监视工具",较通篇 | 方向对但空泛,细节少 |
| 4.5 | CoT      | deepseek-coder | 915字,按"1.现象与怀疑点 2.验证方法"列点 | **结构出现**了,内容仍浅(怀疑点只3个且不具体) |
| 4.6 | few-shot | deepseek-coder | 548字,【现象】【怀疑点】【验证方法】四段复刻模板 | **few-shot 让 coder 的输出结构从"泛"变"准"**,内容仍比 qwen 浅 |

(few-shot 用于此题:给一个"结构化排障思路"的示例,如:现象→怀疑点→验证方法→结论模板)

### 观察目标(不是"谁好",是"模式")

- coder 是否代码/结构任务碾压、开放推理翻车?
- qwen 是否中文理解好、格式遵循差?
- CoT 收益最大的是哪个模型?
- few-shot 是否两个模型都稳定吃效果好?

### 结论(2026-11-10 实测)

- coder 是否代码/结构任务碾压、开放推理翻车?**确认**。运维排障开放题:qwen 知识点密度、工具名、结构全面碾压;coder 要 few-shot 拉扯后结构才像样,内容深度仍不及
- qwen 是否中文理解好、格式遵循差?**前半确认后半推翻**:零样本时格式确实自由发挥(中文键名/嵌套),但加 few-shot 后复刻完美。修正为"零样本格式自由,few-shot 下格式可控"
- CoT 收益最大的是哪个模型?**deepseek-coder**(拒绝回答→不再拒绝、结构从无到有;qwen 收益≈0)
- few-shot 是否两个模型都稳定吃效果好?**都吃但方向不同**:qwen 吃"格式"(键名/枚举),coder 吃"结构"但会跑偏成"写代码解题" —— 对 coder 是双刃剑

## 总结论(全部跑完后填)

| 技巧        | qwen2.5:7b | deepseek-coder:6.7b | 通用建议 |
|:-----------|:-----------|:--------------------|:-------|
| CoT        | 收益≈0(能力区内自发分步) | 有限:降拒绝率、出结构,救不了知识错误 | 推理题给弱模型加,强模型不必 |
| few-shot   | 质变:格式/键名/枚举全对齐 | 双刃:结构出现但跑偏成写代码 | 结构化输出必配 few-shot+通用模型 |
| 幻觉抑制约束 | 完全生效(编造 100%→0) | 完全无效(照编,字数反增 817→1442) | 约束只对通用对话模型可靠;代码模型做问答=高危 |

**给第 4 周"智能问答助手雏形"的 prompt 策略决定**:

- [x] 问答接口默认带幻觉抑制约束(**是**,依据实验三:qwen 100% 生效,coder 无害)
- [x] 结构化输出场景默认 few-shot(**是**,依据实验二:qwen 从自由发挥到精确复刻)
- [x] 推理类问题默认 CoT(**可选**,依据实验一:对 qwen 无益,对弱模型/降拒绝有益;默认不加按需加)
- [x] 模型选择建议:代码类 → deepseek-coder;中文问答/结构化输出/RAG 生成 → **qwen2.5**(工程 `/ai` 默认 model 建议改为 qwen)

## 现象备忘(实验中随手记)

> 撞到意外现象就记在这里:不稳定输出、拒绝回答、中英混杂、重复循环、格式崩坏等。
> 这些"失败样本"在面试里比成功样本更有讲头。

- deepseek-coder 无 CoT 时**直接拒绝领域外问题**:"这是数学问题,请找数学专家"(1.2 第2次)——小模型的任务边界防御行为,CoT 能降低其触发率
- deepseek-coder 把 0.72 说成"**72 折**"(1.4 第2次):计算全程正确,最后一步概念命名错误 —— 数值对≠理解对,判卷要看最后结论
- deepseek-coder 在 2-shot JSON 任务里**写起了 Python 解析代码**(2.4):它把"转换任务"理解成了"实现转换的程序",任务定位惯性压过了示例
- qwen2.5 零样本时**自创嵌套结构**把"地点"拆成{城市,设施}(2.1):零样本下模型会过度设计,示例能压制这种自由发挥
- 约束前缀对 coder 不仅无效,编造字数反而从 817 涨到 1442(3.4 vs 3.5):提示词在代码模型里的权重分布与预期完全不同,"要求不编造"可能被理解为"更详细地阐述"
